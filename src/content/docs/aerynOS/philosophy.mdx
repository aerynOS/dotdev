aerynOS is the collective output of brand new tooling and associated processes, engineered from the ground up to deliver a Linux distribution that focuses on reliability, up front predictability, proven performance, and efficiency.

Our "from the ground up" approach has enabled us to provide atomic updates without requiring reboots or having to utilize containers for package delivery. aerynOS is designed to deliver an ideal level of flexibility and customizability, which stops short of compromising predictability and reliability.

## Stateless (The `/usr` directory is hermetic.)

Most Linux distributions follow the [Filesystem Hierarchy Standard (FHS)](https://refspecs.linuxfoundation.org/FHS_3.0/fhs-3.0.pdf) which patterns the structure for all files and directories on Unix conventions. Under the FHS, package files can be installed to multiple directories, many of which the user is able to interact with (config files for instance).

In aerynOS, packages are forbidden from writing files to any but the `/usr` directory, (transaction and system triggers excepted).* The `/usr` directory is intended for system use only. Any user initiated changes made will revert and any user downloaded files disappear when next the system updates. (*Triggers are small scripts that run at the tail end of a package installation.)

We alter the system packages and configurations to give them resilience, ensuring they still operate even in the absence of user-provided configuration. This guarantees that sane defaults are baked in at all levels. This guarantees that reversion to factory defaults are automatic in the event of corrupted or conflicting user config files that must be deleted from the `/etc` directory. Thus the possibility of 3-way merge conflicts on package updates is completely eliminated.

The stateless Linux concept was originally proposed by Red Hat in 2004 and the idea has continued to evolve from there. aerynOS leans towards the approach developed by Clear Linux, which we are continuing to refine.

### Transaction Triggers

Transaction triggers are run at the end of a transaction in an ephemeral container (Linux namespace) and may affect the contents of the transaction-specific `/usr` tree. This is useful for interdependent packages that need to dynamically produce plugin registries, for example.

### System Triggers

System triggers do not run in an isolated container, but instead are run within the context of the host system after the transaction has been successfully built and applied. It is these (minimally used) triggers that invoke `systemd-tmpfiles`, `systemd-sysusers` etc. For these cases we take special care to ensure that our default configs are sane and that a rebuild is always possible.

## Atomic updates

An atomic update is a series of changes to a system that are treated as a single, indivisible operation. If any part of this update fails, the entire update is canceled and all prior parts of the incomplete update rolled back. Either an update completes fully as intended, or the system is returned to the state it was in before the update was attempted, thereby completely avoiding bricked installs.

But atomic updates in aerynOS are different. Most Linux distributions that favor atomic updates employ an A/B switch model, swapping one read-only file system for another upon reboot. In aerynOS, atomic updates are managed by a system state manager/package manager called `moss`. Not tied to using read-only file systems, `moss` can employ XFS, ext4 or F2FS file systems. Additional file systems will be tested for future consideration.

Because aerynOS utilizes a stateless design where packages are permitted installation to a single directory - the `/usr` directory - it can innovate in its approach to atomic updates. Packages are created in a custom `moss` format called `.stone` files, which contain a deduplicated set of hashed files which are compressed using `zstd`.

### Content Addressable Store (CAS)

When a `.stone` file is installed, its contents are decompressed and stored in a global deduplicated content-addressable-store (CAS) located under a directory named `/.moss/`. This CAS contains all files for all `.stone` packages installed on the system. Also located under `/.moss/` is a database containing relevant metadata.

### Hardlinking

As part of the final stages of an atomic transaction, `moss` creates (or “blits”) a new `/usr` directory of [hardlinks] (https://www.virtualcuriosities.com/articles/4507/how-hard-links-and-inodes-work-on-linux) to the global content addressable store (CAS). It then instantly swaps this new `/usr` hardlink directory into place using the `renameat2` Linux kernel syscall, with the `RENAME_EXCHANGE` flag. Thus the old path is atomically exchanged for the new. On modern NVMe drives, this atomic swap takes less than 1 second.

`Moss` archives every `/usr` directory replaced in every transaction, allowing the user to roll back to earlier system states at will. Archival storage of this sort is practical because hardlinks take up a trivial amount of space on disk; also because the CAS contents are deduplicated every time. So one can retain many system snapshots with minimal overhead. However these may also be pruned as desired.

## Bootloader

Our BLS compliant boot management tool, `blsforme`, provides the `systemd-boot` bootloader with convenient access to the last 5 `moss` system states as loadable options at boot time. It is here the user can instantly revert to any of the previous 4 states at will.

## Self healing

As part of our boot management solution, moss tracks each transaction with a discrete ID which is encoded into the kernel command line. During "early boot" into the initial RAM file system (`initramfs`) before pivoting to /sysroot, this ID enables the kernel to synchronize with the proper corresponding root file system (`rootfs`).

### What are the implications of all of this?

On a typical Linux distribution running Gnome, say on a whim you delete gtk3, GDM, and gnome-shell. You certainly can't log back into the Gnome session. At best you can access to a console prompt to log in to the command line shell. In aerynOS on the other hand, you can interrupt the bootloader on reboot by mashing the spacebar, and there select the prior entry, thus automatically switching your boot to an archived  /usr filesystem transaction where gtk3, GDM and gnome-shell still exist.

Or say that on a traditional Linux distribution you remove a critical component such as `glibc` from your system and then reboot. Trouble. But do the same with aerynOS and reboot, and the system  immediately recognizes the impossibility of successfully continuing the current boot, and automatically rolls back to the prior bootloader entry associated with a functioning /usr directory. Within a second or two you are dropped back into a live working desktop.

## Repository Management 

Versioned repositories are now a reality with aerynOS. We currently offer two "Update Streams": the default stream we call "unstable," and the testing stream we call "volatile."
Being that we are a rolling release distribution, we land packages in our volatile stream first for testing. After a period of time (usually 1 to 2 weeks), we sync the state of the volatile stream to the unstable stream, so the wider user community can then receive updated packages. Each stream sync from volatile to unstable has a corresponding addressable tag, which acts as a snapshot in time that we can return to and test from.

## System model

By default, aerynOS operates as a standard "imperative" Linux distribution. We have also implemented the concept of an (optional!) install-time declarative system-model where a user can define (within the `/etc/moss/system-model.kdl` file), which exact packages they want from which repository. `moss` will then keep the system in sync with this system-model as updates arrive. Due to the use of addressable tags, our system-model is able to go even further and enable users to define a specific tag on our unstable repository, thus making it akin to a fixed point release model. The user can change this tag and fix to another tag at any time, or revert to the rolling release model if desired. Such flexibile design enables users to replicate their system-model across different installations and to share specific system-models with the aerynOS team for the purpose of troubleshooting.

## Package Management 

We have been simplifying our package management process through automation where possible, in order to reduce the mental burden for our packagers. For example:

- For updating an existing package in our repository, we have a tool that searches the availablity of a new release. Finding one, it updates the recipe accordingly. The packager then need only accept, save, build and test the package for viability.
- For creating a new installable package to add to our repository, we have a tool that scans the package source file and creates from it a recipe, pre-populated with relevant information. The packager has then only to fill in any missing information, save, build and test the package for viability. 
    
## Package Building

We currently have four permanent build servers dedicated to official packages that land in our repositories, plus a few more that assist during very large build queue processing. Tooling has been developed to assign smaller builds to less powerful machines, and the larger and more complex builds to more powerful ones. Tasks are automatically analysed against build criteria and assigned priority accordingly.
